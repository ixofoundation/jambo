# Installable app (PWA)

How the home-screen app works today. The roadmap is in `docs/pwa-plan.md`; this covers Phases 1 to 3.

## Files

| File | What it does |
| --- | --- |
| `public/manifest.webmanifest` | Name, colours, icons, home-screen shortcuts (Wallet, Tasks, Profile). |
| `public/icons/*` | App icons. Made by `scripts/make-pwa-icons.py`. |
| `public/offline.html` | Shown when a page can't load and no copy is saved. No scripts or styles from the network. |
| `sw/sw.js` | Service worker source. **Edit this one.** |
| `public/sw.js` | Generated by `scripts/build-sw.js` on `yarn build`. Gitignored. |
| `sw/kill-switch.js` | Worker that removes itself and every JAMBO cache. See "Kill switch". |
| `lib/pwa/serviceWorker.ts` | Registers the worker, tracks a waiting update. |
| `lib/pwa/install.ts` | Install offer state (Android prompt, iOS instructions, "Not now" pause). |
| `components/Pwa/Pwa.tsx` | Mounted in `_app`: "A new version is ready" pill, the install sheet, and the route warm-up. |
| `lib/pwa/userData.ts` | Last balance and last confirmed collection roles, saved per account, wiped on logout. |
| `lib/pwa/warmUp.ts` | After sign-in, downloads the main screens' code while the phone is idle. |
| `lib/pwa/outbox/` | Offline claims: photos and claims kept in IndexedDB (`db.ts`, `heldFiles.ts`) and the sender (`claims.ts`). |
| `components/Pwa/Outbox.tsx` | Runs the sender; the "Waiting to send" list on Tasks and the collection page. |

## What is cached

| Request | How |
| --- | --- |
| `/_next/static/*` | Cache first. File names are hashed, so each chunk downloads once, across deploys. Max 250. |
| Page loads | Network first. If the network fails, or takes over 6 seconds, the last saved copy of that page; with no copy, `offline.html`. Max 40 pages. One copy per path; the query string is ignored. |
| `/images/*`, `/icons/*`, `/favicon.ico`, Google Fonts | Saved copy at once, refreshed in the background. Max 80. |
| Images from other sites (opportunity photos on IPFS, cellnode) | Saved copy at once, refreshed in the background. Max 150. Fetched in CORS mode; a site that refuses CORS is loaded normally and not saved (an opaque copy would take ~7MB of the phone's storage quota each). Wiped on logout. |
| Everything else | Not touched. |

At install, the worker also saves `/`, `/tasks`, `/wallet` and `/profile`, so the home-screen app opens offline on those even if the user never opened them.

Never touched, on purpose: `/api/*`, `/auth/*` (one-time sign-in codes), `/cleanup/*` (the World Cleanup Day app, which has its own worker), `/ingest/*` (analytics), and every other origin. Chain, Matrix, YellowCard, KYC and balance calls all fall here, so none of them are cached.

Pages are safe to cache because none use `getServerSideProps`: the HTML is the same for every user, and user data loads afterwards in the browser.

## Offline data (Phase 2)

Data comes from redux-persist (`jambo-cache` in localStorage), not the worker: opportunities, collections, protocol entities, form templates, profiles and drafts were already saved there. Phase 2 makes the app use them when the network fails:

- **Claim forms open offline.** `fetchProtocolEntity` (`utils/entity.ts`) treats a saved entity as stale after 5 minutes. When the refresh fails, it now returns the saved copy instead of nothing. Collections and form templates were already read from the saved copy.
- **"New Claim" shows offline.** The collection page checks the user's permission on chain every 5 seconds. Each successful check is saved per account and collection; when the check fails, the last saved permission is used. The chain still checks for real when the claim is sent.
- **Balance shows offline.** The wallet saves the last good total and shows it with "As of 10:42" until a live read arrives. Only the display uses it: the USDC upgrade logic and withdrawals still get live numbers only.
- **Screens load offline.** After sign-in, while idle, the app downloads the code for Deck, Tasks, Wallet, Profile, the collection page and the claim form. Code a screen loads later on its own (the survey styles, maps, the PDF viewer) is saved the first time that screen is opened online.

**Save-Data.** When the phone asks to save data (Chrome "Lite mode", Android Data Saver) or the connection is 2G, the warm-up is skipped. Next.js already skips its own link prefetching in the same cases. Smaller images are not possible yet: images come straight from IPFS and cellnode, which don't resize.

**Logout** (`clearAllState` in `providers/auth.tsx`) removes the saved balance, every saved collection permission and the remote-image cache. App code and page caches stay: they hold no user data, and keeping them saves the next user's data.

## Offline claims (Phase 3)

A youth can do a task with no signal, submit it, and it sends itself later.

**Photos.** In a plain claim form, a photo picked with no connection is compressed as usual and kept on the phone (IndexedDB, `jambo-outbox`). The answer gets a placeholder, `{"jamboHeldFile": "<id>", …}`, and the form previews the photo from the phone. A photo whose upload fails *because the connection dropped* is held the same way; one the server refuses still fails as before. Files over 100MB are not held.

**Submit.** A plain claim submitted offline, or with photos still waiting, is saved to the outbox instead of being sent: the draft is cleared, the user goes back to the collection, and a toast says it will send when they are back online. `submitForm` in `screens/collectionForm.tsx` is unchanged; the only change there is the branch before it. Any other form (sub-claims, approve-payment, applications) still needs a connection, and is blocked with a message if it holds a photo that hasn't uploaded.

**Sending** (`lib/pwa/outbox/claims.ts`) runs in the page, not the service worker: the signing keys and Matrix login are in the page's storage, which a worker can't read. So claims go out when the app is open and online: on sign-in, when the connection returns, when the app comes back to the front, every 2 minutes while any are waiting, or on "Send now". Not with the app closed.

The steps match `submitForm`'s, with the photo uploads first. Progress is saved after each step, so a retry resumes:

1. Upload each held photo (VFS, or the Claim Bot if VFS isn't available), save its reference.
2. Register the signing key on the DID, if missing.
3. Sign the credential, **once**. The claim ID is the hash of the signed credential, so re-signing would make a different claim.
4. Save to the Claim Bot, save the claim ID.
5. If blocksync already has that claim ID, stop: an earlier attempt landed.
6. Sign and broadcast `MsgSubmitClaim`; the tx hash is saved before broadcast.

A lost connection stops the run and keeps everything. A refusal is saved on that claim and shown ("Not sent: …"); the others still go. A broadcast that isn't confirmed in time shows "Sent. Waiting for the chain to confirm it" and is finished on the next round. A refusal from the chain is double-checked against blocksync before it counts.

The claim is signed when it is **sent**, not when it was filled in, so the credential's issue date is the send date.

**Sessions and logout.** Queued claims belong to the account that made them and only send when that account is signed in. They survive the 24-hour session expiry. Settings → Logout deletes them, after a warning and a second tap. The deck's "Log out & try again" (Vault recovery) keeps them.

**Not covered:** sending with the app closed; sub-claims and approve-payment claims offline; claim-form code that was never loaded online on that phone (see "Screens load offline" above).

## Updates

Each deploy writes a different `public/sw.js` (the commit is stamped in), so phones notice the new version. It installs in the background and then **waits**. The app shows "A new version is ready · Update". Tapping it switches over and reloads.

- The pill never shows on `/auth/*` or on the claim form, so nothing can reload a half-finished form or the sign-in step.
- Installed apps stay open for days, so the app also checks for a new version when it comes back to the front, at most every 30 minutes.
- Page loads go to the network first anyway, so a full reload always gets the newest pages and code.

## Install offer

- **Android / desktop Chrome:** the browser's own banner is held back. After the user submits a claim, a sheet offers "Install", which opens the browser's install dialog.
- **iPhone / iPad:** no install API exists. The sheet shows "Share → Add to Home Screen".
- "Not now" pauses the automatic offer for 14 days.
- Profile has an "Install the app" row whenever the phone can install it and hasn't.
- Nothing shows once the app is open from the home screen.

## Analytics

Every event carries `display_mode`: `standalone` (opened from the home screen) or `browser`. Events: `pwa_install_prompt_shown`, `pwa_install_prompt_result`, `pwa_install_prompt_dismissed`, `pwa_installed`, `pwa_update_accepted`. Home-screen launches open `/?source=pwa`; shortcuts add `?source=pwa-shortcut`.

## Kill switch

If a worker release breaks the app, set `NEXT_PUBLIC_SW_KILL_SWITCH=1` in the Vercel environment and redeploy. That build:

1. ships `sw/kill-switch.js` as `public/sw.js`. Phones fetch it, it deletes every `jambo-*` cache, unregisters itself, and reloads open pages.
2. stops the page from registering a worker, and removes any it finds.

Both are needed: without (2), each reload would register the kill switch again and reload forever. Remove the variable and redeploy to turn the worker back on.

## Local testing

`next dev` does not register the worker (it fights with hot reload). To test it:

```powershell
yarn build
```

```powershell
yarn start
```

Then open http://localhost:3000. Chrome DevTools → Application shows the manifest, the worker and the caches. To test offline, stop `yarn start` and reload. For the worker in `next dev`, set `NEXT_PUBLIC_SW_DEV=1`, and unregister it afterwards in DevTools.

## Icons

The current icons are made from `public/images/yoma-dark-min-logo.png`, which is only 250px. Replace them with a 1024px square source:

```powershell
python -I scripts/make-pwa-icons.py path\to\icon-1024.png
```
